# RAG 召回评测：怎么写、怎么跑、怎么读

> 2026-10-17 · 第一次基线 · 对应用户资料库（47 份资料）
> 评测器：`rag/recall_eval.py`（hit@k / MRR，纯函数 + CLI）

## 1. 它是用来干什么的

**检索层的回归测试 + 决策尺子**：用一批固定的「问题 → 应该命中哪份资料」，量出检索准不准。

它回答三个具体问题：

1. **向量腿值不值得留**（它要花 embedding 成本、40MB 索引，还要处理签名不匹配与单进程锁）；
2. **RRF 权重是不是拍脑袋**（现在 `vector=1.0 / fts5=1.0`）；
3. **这次改动有没有把检索弄坏**（改 chunking / embedding 模型 / Qdrant 版本 / FTS 分词之后）。

**它不是**：面向用户的功能、回答质量评测（只看资料召回）、跨系统打分、LLM 自动评分。

## 2. 用例格式（JSONL，一行一条）

```jsonl
{"query":"求一个点到所有点最便宜的路，每次挑最近的点扩出去","expect_sources":["Dijkstra.md"],"kind":"paraphrase","source":"human"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `query` | ✅ | 学习者会问的那句话（自然语言 15–40 字） |
| `expect_sources` | ✅ | 允许命中的**文件名 basename**（不是路径、不是标题；chunk id 会随重切变化）；判定是「任一命中 top-k」 |
| `kind` | ❌ | `keyword`（默认，关键词型，防回归）/ `paraphrase`（换述型，只有语义检索才可能中） |
| `source` | ❌ | `generated`（默认）/ `human` |

## 3. 怎么写（六条规则）

| # | 规则 | 原因 |
|---|---|---|
| R1 | **不许出现资料标题或目录关键词** | 出现了就是给 FTS 送分，测不出向量腿 |
| R2 | 用**学习者口吻**提问，不要堆关键词 | 「贪心 局部最优」是关键词列表，不是问题 |
| R3 | **换述**：换句式、换说法、加场景或追问 | 只有「换了说法仍指向同一份资料」才测语义 |
| R4 | 期望要精确；多份都算对就全列 | 判定是「任一命中」，列全不会矛盾 |
| R5 | 答案必须**真的在资料里** | 资料里没有 → 是内容缺失，不是检索失败 |
| R6 | 一题一义 | 一句话问两件事，命中了也说明不了什么 |

**自检**：把问题里的每个词单独拿去搜，如果光靠一个词就能命中 → R1/R3 没做到，重写。

**数量与结构（本次采用）**：24 条换述 + 5 条关键词对照 = 29 条。关键词组用来证明「没把关键词能力测坏」。

## 4. 怎么跑（两条命令）

**前置**：先停掉开发服务器 —— 本地 Qdrant 是单进程存储，服务在跑时外部进程打不开库，向量腿必然不可用。

```powershell
# ① fts_only 对照：把 embedding 关掉（占位 provider）
.venv\\Scripts\\python.exe -m rag.recall_eval --workspace note/vault --cases note/vault/.bobodan/eval/cases.jsonl --modes hybrid --k 5 --embedding-backend local

# ② 真实配置（hybrid）：不传 --embedding-backend 即用 config.yaml
.venv\\Scripts\\python.exe -m rag.recall_eval --workspace note/vault --cases note/vault/.bobodan/eval/cases.jsonl --modes hybrid --k 5
```

跑完请重启服务。真实库用例文件在 `note/vault/.bobodan/eval/cases.jsonl`（`note/` 已被 gitignore，真实内容不进仓库）。

## 5. 2026-10-17 基线（29 条用例）

| 组 | fts_only hit@5 | hybrid hit@5 | fts_only MRR | hybrid MRR |
|---|---|---|---|---|
| 换述（24 条） | 0.875（21/24） | **0.958（23/24）** | 0.550 | **0.660（+20%）** |
| 关键词（5 条） | 1.000（5/5） | 1.000（5/5） | 0.900 | **1.000** |
| 合计 | 0.897 | **0.966** | 0.610 | **0.718** |

**逐题诊断**：向量腿**找回 3 条** FTS 漏检的题（流水线写法 → 15、几个 AI 分工 → 26、Dijkstra → Dijkstra.md）、**弄丢 1 条**（小模型先猜大模型验 → sample.md）、**零双向漏检**。

**结论：保留向量腿（hybrid 作默认）。** 理由：

1. 关键词组零退化 ✓（1.000 → 1.000，MRR 反而升到 1.000 ✓）；
2. 换述组找回 3 条、只弄丢 1 条 ✓（净 +2 ✓）；
3. MRR 提升 **+20%** ✓ —— 排序质量明显更好（用户更少看到无关结果排在前面）；
4. hit@5 只 +8.3pp：**注意这是天花板效应** —— FTS 换述基线已 87.5%，绝对提升上限只有 12.5pp，原方案里「≥15pp」的判据在数学上不可能达成（已修正，见下）。

## 6. 决策规则（2026-10-17 修正版）

原规则「换述 hit@5 提升 ≥15pp」在被测基线较高时不可达，改为：

> 保留向量腿需**同时**满足：
> 1. 关键词组 hit@5 **不下降**（任何下降即回滚）；
> 2. 换述组**找回条数 ≥ 弄丢条数 + 2**；
> 3. 换述组 MRR 相对提升 **≥10%**。

本次：① 满足（0 下降 ✓）；② 满足（找回 3 / 弄丢 1 ✓）；③ 满足（+20% ✓）→ **保留**。

## 7. 已知问题与后续

1. **`sample.md`（投机解码）那条退化**：fts 排第 3、hybrid 掉出前 5 —— 疑似 RRF 权重让向量结果挤掉了关键词命中。后续可试验 `vector weight 0.8` 看是否同时保住两者；现记录为待观察项。
2. **排名有升有降**：约 6 条排名提升、4 条下降，这是 RRF 融合的正常代价，不是 bug。
3. **样本量偏小**：24 条换述 → 每条约 4.2pp，2–3 条的差异仍在噪声范围。建议后续扩到 40–60 条（方案 §5.2 的 L3 全量）。
4. **两种配置要跑两次进程**：CLI 已支持 `--embedding-backend`，但还没做「一次跑两配置出对比报告」的入口。

## 8. 什么时候必须重跑

改以下任一项之后：chunking 策略、embedding 模型或维度、Qdrant 版本或集合配置、FTS 分词或查询构造、RRF 权重或 top_k、检索器缓存逻辑。
