## 1. 结论：路线较完整，但还没有形成可靠的发布决策体系

**现有路线值得沿用，不需要重新发明一套路线图。** W1 学习闭环、W2 检索、W3 体验、W4 运行时与数据、W5 发布的结构合理；产品边界、失败恢复、数据保护、技术约束和发布事项也已有相当细致的规划。

真正不足的是三件事：

1. **状态不够统一。** 同一个任务在不同章节仍能看到“未做”“部分完成”“已完成”；历史记录、当前状态和未来方案混排，读者需要自行拼出下一步。
2. **功能验收领先于效果验收。** 能生成题、记录作答、显示掌握度，不等于题目可靠、批改合理、学习状态一致，更不等于用户长期学会了。
3. **发布门禁没有集中闭合。** 运行时、数据恢复、视觉、学习质量分别有要求，但缺少一张绑定同一提交、环境和证据的发布候选验收表。

**建议：保留 W1–W5，把“学习语义一致性、证据表达、可重复集成验收”补成主线，再进入受控 Windows 预发布。不要以新增更多功能来证明路线完善。**

## 4. 路线文档本身的缺口

### 4.1 当前状态分散，唯一入口不够“唯一”

可直接定位的例子：

- `ROADMAP.md` 头部版本仍是 v1.4/2026-09-25，正文已有 2026-10-17 结果。
- W2 开头仍保留 G4“未做”的复测描述；G4 表格写“部分完成”；§1.1 又写 2026-10-17“已完成”。虽然有日期和纠正说明，仍要求读者手工判断。
- `PROJECT_GUIDE.md` 开头仍写“下一步 A2”，W1 交付清单却已经写 E1–E16 交付。
- `W1_DELIVERY.md` 保留“39 个提交全在本地、GitHub 看不到”的历史现场叙述；当前公开仓库已包含相关代码。应标为当时的快照，不可当成当前分支状态。
- `QUESTION_BANK_DESIGN.md` 顶部概述 S1–S5 已交付，后面状态表已记录 S6/S7 交付；顶层摘要没有同步。

建议把路线首页控制在一至两屏，固定四块：当前基线、当前主批次、下一批候选、发布阻塞项。历史交付与探针记录继续保留，但移到交付日志，不在首页重复维护状态。

### 4.2 Wiki 产品边界有冲突，不能靠读者猜

`LIBRARY_TREE_DESIGN.md` §3.1 写“Wiki 彻底停用，不再生成”；README、项目指南和设计规范仍描述高级 Wiki 维护，当前代码也仍保留相关计划/应用路径与设置项。

这首先是**产品规范冲突**，不能仅凭保留代码就断言违规：文件树设计也明确允许复用 Wiki 底座。

建议先记录一条明确决策，区分：

1. 旧 Wiki 数据是否只读保留；
2. 新 Wiki 生成是否允许、是否在正式 UI 暴露；
3. Wiki 底座能否继续服务 AI 文件整理；
4. Wiki 是否允许成为回答/出题证据。

建议默认主路径不生成 Wiki，保留历史读取与恢复；如维护生成能力，应通过明确高级入口及统一开关表达。最终选择应由项目负责人确认，不能由本报告覆盖此前已定的用户决策。

### 4.3 “已交付”与“完整验收”被混用

E6 的历史/纯函数/展示链路交付确实成立，但不能据此把学习状态一致性也视为完成。文档已经诚实列出尾项，问题在于尾项影响大于“细节”的命名。

建议保留父项已交付记录，同时创建独立尾项，写清风险：

- `E6.1` 作答历史、推导值、界面与 Agent 读取：保留历史完成状态。
- `E6.2` 掌握状态、排序、计划完成与调度的统一消费契约：待实施/验收。
- 不把“课程选择器”“跨笔记选择器”和“学习状态一致性”放在同一级小尾巴中处理。

### 4.4 专题方案需要回到统一排期

前端 v2、设置 v2、UI 审计都有自己的编号和完成记录。设计可以分文档，但排期不应分裂。每一项未来工作都应映射到 W1–W5，并注明是硬门禁、体验改进还是暂缓项。

例如：字体体积和 IME 错误可以是发布问题；更多主题、弹簧动效和组件行数目标通常不能自动阻塞核心产品试用。

## 5. 现有 W1–W5 如何补强

### 5.1 W1：学习闭环，从数据打通走向判断一致

#### A. 统一掌握度语义（最高优先级）

前轮实测同一概念连续答对两次：

```json
{"status":"mastered","score":0.30000000000000004,"mastery":0.8,"evidence":2,"mastery_source":"history"}
```

代码中旧调度器更新 score/status，新引擎另算 mastery，计划完成仍读取 mastered。不同字段可以有不同职责，但现在它们容易被混读为同一种“能力”。

**不要求替换 SM-2。** 调度算法可以继续存在；需要统一的是它与能力估计、业务状态之间的契约。

建议：作答事件作为事实，能力估计作为可版本化推导结果，复习日期作为调度结果。展示、排序、计划完成、Agent 读取必须消费同一明确契约；旧 score 迁移、废弃或重命名，不能继续含糊并存。

验收：

- 相同历史重复计算得到相同结果；记录算法版本。
- 单次、连续两次、先错后对、partial、重复提交、手动标记都有明确行为。
- 重复提交不能新增有效学习证据。
- 界面、API、Agent 与计划完成对同一概念的解释一致。
- 原始事件保留，迁移失败可恢复，手动标记与系统推断分开。
- 同题反复练习、看提示后答对是否降权，先制定规则与数据字段；不要声称仅两次答对就证明长期掌握。

#### B. 补题目与批改质量验收

已有三态判分、来源绑定、错题变式和题库，不应重做；缺的是语义质量验证。

建议建立独立于 CI 的受控模型评测：题面可答、正确答案成立、干扰项合理、简答评分要点清楚、反馈不与原文矛盾。记录模型、提示词版本、资料快照、成本和错误类型。

短期先使用少量人工审阅样本，不要立刻建设复杂自动裁判。允许用户对批改提出异议；改判后明确是否重算学习状态，并留下记录。

#### C. Today 落在 Chat 起始态

遵循既有 chat-first 决策，不新增 dashboard。回访起始态最多突出：继续上次、今天建议复习、开始新学习。明确建议依据和预计任务量；用户随时可直接提问。

复习中的到期、错题和薄弱点可按概念聚合展示原因，但保留不同数据含义，不能为了去重而丢掉具体错题。

### 5.2 W2：沿用评测器，把“召回”与“可信回答”分开

#### A. 承认并保留现有真实基线

以下是项目 `RAG_EVAL.md` 的历史记录，本次未独立复跑私有资料库：

| 分组 | FTS-only hit@5 | hybrid hit@5 | FTS-only MRR | hybrid MRR |
|---|---:|---:|---:|---:|
| 24 条换述 | 0.875 | 0.958 | 0.550 | 0.660 |
| 5 条关键词 | 1.000 | 1.000 | 0.900 | 1.000 |
| 合计 29 条 | 0.897 | 0.966 | 0.610 | 0.718 |

这足以支持在该资料库继续保留 hybrid，也体现了评测后再决定的正确习惯。它不能直接证明所有学科和文档类型均有同样收益。

改进建议：

- 沿现有计划扩到 40–60 条人工样本；再根据失败分布扩充，而非追求数量。
- 加入无答案、跨章节、矛盾资料、同名文件等组别。
- 当前期望使用 basename，跨文件夹同名文件可能混淆。迁移为带资料库范围的稳定标识或规范化相对路径，并维护版本映射。
- 文档命中与片段支持分别计量；文档找对不代表供给模型的片段正确。
- 不要求换述题刻意消除所有可词法命中的词。现有 FTS 在换述组已达 87.5%，说明“换述只有向量能中”不是合理假设。样本应代表用户真实提问。
- 现有阈值在观察结果后修订过，原因合理，但下一轮应提前冻结判据并留保留集，避免在同一批题上反复调规则。
- 记录命中收益之外的延迟、成本、锁冲突与降级比例。

#### B. 新增证据表达与结论支持契约

前轮单独调用证据策略，将“Dijkstra 要求非负权”作为命中内容，回答给成“Dijkstra 支持所有负权图”，仍得到 allow=True。此复现证明该策略检查“发生了成功检索”，不证明真实模型必然产生该错误，也不是对整个系统所有防线的穷尽性攻击测试。

补强分两阶段，避免一次引入昂贵的全量自动事实核查：

1. **先做到不夸大保证**：区分“检索到资料”和“此结论有对应原文”；引用 ID 来自本轮证据，标记资料版本和缺失来源；有矛盾时展示冲突而非强行拼合。
2. **再提高支持度检查**：重要结论绑定具体引文，使用规则/模型辅助检查并对样本人工复核；检查结果是风险信号，不包装为绝对正确认证。

验收至少覆盖伪造引用、无答案、资料与结论矛盾、资料更新后引用失效、混合本地与通用知识。

#### C. 维持 OCR 暂缓，但保证提取边界可见

项目已明确首发不做 OCR，不建议本轮推翻。优先保证扫描页、空白页、表格和无文字幻灯片的报告准确，缺失正文不会被当成完整资料用于出题。G5 更复杂的目录恢复要由真实 PDF 失败样本驱动。

### 5.3 W3：从全面重构转向任务成功

设置区 S1–S5、CSS 拆分与逐页视觉整改已有文档记录。继续投入应优先解决真实卡点：

- 引导内能完成连接配置和第一份资料导入，不把关键动作推迟到引导结束后。
- 无密钥时可试用明确标记的示例或先阅读资料，不伪装成 AI 已就绪。
- 练习开始前让资料范围和学习目标可见。
- 处理 UI 审计遗留的记忆徽标统计口径；它与掌握度问题一样属于语义一致性，不只是样式。
- 窄屏阅读器双滚动、键盘焦点、IME 误提交按实际复现优先。
- 更新 README 截图，注明基线提交和示例数据；不要用旧图重新立已经修复的任务。

对前端 v2 的一个技术修正：将状态搬入 Zustand 可以减轻闭包依赖，但全局 store 不会自动消除耦合。DOM ref 不必一概入 store，actions 带副作用也不能称为纯函数。迁移必须有资料库/session/run 作用域、切换取消和过期结果拒收；文件行数只能作提示，不能作唯一验收标准。

### 5.4 W4：只建设被正确性和发布实际需要的底座

优先项：

- 学习事件与迁移的幂等性，跨库/跨会话结果隔离。
- 文件操作部分成功、异常退出后的台账和恢复。
- 工具超时后的真实状态：停止等待不等于工作线程停止，晚到结果不能污染新任务。
- 模型调用与任务的总预算，失败/取消后账本与用户提示一致。
- 资料库和应用数据的整体备份恢复演练。

暂缓项：没有具体阻塞时，不推进自主循环、Memory Dream、工具 BM25 搜索、复杂技能画像或大范围事件源改造。已有代码可以保留，但不让“参考项目有”成为新排期理由。

备份要区别两种能力：题库 S7 已记录题库级 JSON 备份/恢复；它不等于资料库、会话、笔记、个人知识、偏好和应用注册信息的整体恢复。全量恢复方案还要明确密钥是否排除、是否重新配置，以及向量索引是备份还是重建。

### 5.5 W5：拆分发布阶段，防止门禁无限膨胀

**现有 W5 候选门禁通过，不等于正式发布所有门禁通过。** 建议分三层：

| 阶段 | 必须通过 | 可以继续暂缓 |
|---|---|---|
| 开发者本地 Web 验证 | 核心契约、临时库集成、来源表达、无静默丢数据 | Electron、签名、自动更新 |
| 受控 Windows Prerelease | 干净机器安装、sidecar 生命周期、数据恢复、升级/卸载契约、基本学习质量验收 | 更多主题、动效、跨平台安装包、OCR |
| 扩大分发 | 多批用户任务验证、质量回归可重复、支持与诊断路径可用 | 通用 Agent 平台和大而全工作台仍无必要 |

维持已有 Windows-first 边界；不把本评审 Linux 环境的路径失败直接判为 Windows 产品失败。但应写清源码运行支持范围，清理测试中的平台假设。

## 7. 四周实施建议

这是顺序建议，超过容量时顺延后续项，不缩减正确性验收来凑日期。

### 第 1 周：状态清账与学习一致性

- 完成 GOV-01，确认 Wiki 边界与发布候选范围。
- 完成 E6.2 设计与关键迁移/回放用例，推进统一契约。
- 固定来源标签的准确用语，建立反例样本。
- 输出：一张可读的当前路线表、一份学习状态契约、一组能证明旧问题的测试。

### 第 2 周：真实集成与证据表达

- 完成 E6.2 与 EVID-01 最小范围。
- 使用临时资料库跑通导入、引用、练习提交、复习、重启恢复。
- 模型通过 ScriptedProvider 控制，业务服务和持久化保持真实。
- 输出：可重复运行的集成命令和失败报告，不依赖作者私人 vault。

### 第 3 周：效果评测与首次路径

- 扩充现有 G4 样本，提前冻结判断规则。
- 小规模真实模型题目/批改评测，使用预算上限和人工复核。
- 落实 Chat 起始态 Today 与首次成功路径。
- 并行准备备份清单和恢复演练环境，不临时重写整个运行时。

### 第 4 周：恢复演练与受控试用

- 完成数据恢复、升级失败和 sidecar 异常场景。
- 邀请约 5–8 名符合目标场景的用户观察使用，重点记录卡点。
- 数据安全和核心契约通过后，决定是否进入 Windows Prerelease；安装工程若尚未完成，继续本地 Web 试用。
- 输出：Go/No-Go 清单、已知限制、下一批真实问题，而不是新增一批没有验证的功能。

## 8. 验收矩阵：需要什么证据才算完成

### 8.1 确定性门禁

| 场景 | 通过条件 | 建议层级 |
|---|---|---|
| 导入成功/部分失败/取消/重试 | 结果与实际文件和索引一致，已完成部分可用 | 真服务 + 临时库 |
| 检索为空或证据冲突 | 不冒充“资料支持”；错误状态可解释 | 策略/服务 + 模型样本 |
| 生成练习 | 题目、来源、练习会话绑定一致，失败不产生假完成 | 真服务 + 脚本模型 |
| 提交与重复提交 | 同一次作答只产生一次有效学习事件 | 存储/服务 |
| 学习状态 | UI/API/Agent/计划使用一致语义 | 服务契约 + 少量 UI |
| 切库、切会话、重启 | 不串数据，晚到结果不覆盖新上下文 | 集成 + 少量浏览器 |
| 资料移动与撤销冲突 | 引用跟随或明确失效，不覆盖用户新文件 | 故障注入 |
| 整体备份恢复 | 干净目录恢复后关键记录和引用可核对 | 发布候选演练 |
| 模型失败与取消 | 失败不等于答错，不重复扣进度，成本可说明 | Provider 契约 + 集成 |

### 8.2 真实模型与用户效果验证

真实模型评测不要混入每次提交必须通过的快速 CI。采用固定版本、固定资料、受控预算的发布前或模型升级评测，按错误类别留样本，不只记一个总分。

建议记录以下指标，先建立基线，再冻结目标：

- 首次独立完成“导入 → 练习 → 看懂反馈”的比例和耗时。
- 题目可答性、参考答案错误、反馈矛盾、批改争议数量。
- 用户能否解释题目为何错、来源在哪里、下一步为何安排。
- 隔天或一周后的变式题表现；区分看答案后的即时正确与延迟保持。
- 完成一次有效闭环的用户数，以及次日/一周后的返回情况。
- 每次有效闭环的调用成本、等待时间、失败率。

5–8 人的小样本用于发现障碍，不足以证明统计显著的学习增益。若未来对外声称“提高学习效果”，需要更严谨的对照设计。内部试用也不应为了指标而默认上传用户私人学习内容；可采用本地统计和自愿导出。

## 10. 哪些方向应继续坚持，哪些先收住

### 继续坚持

- Python + FastAPI + SQLite + React 的现有架构。
- FTS-only 可独立工作、hybrid 有评测依据时增强。
- 来源由程序绑定、文件操作可恢复、用户数据不被静默改写。
- Chat 是入口，资料、练习、复习是学习主线。
- 图谱辅助定位与学习，不成为使用门槛。
- 风险驱动测试和 ScriptedProvider，外加少量真实后端关键路径。

### 暂时收住

- 为追随参考项目而新增自主循环、记忆梦境、技能画像和工具搜索。
- 为达到文件行数目标而进行全局状态大迁移。
- 已有视觉审计通过后再做一轮全产品换皮。
- 缺少 PDF 失败样本就全面建设 OCR 或复杂解析体系。
- 首发同时要求跨平台安装包、更多主题、自动更新和通用工作台。
- 在学习状态不一致时，用庆祝动效或进度环强化“已经掌握”的错觉。

## 11. 最终判断

**这条路线已经具备“能继续开发”的完整性，但还欠缺“能可靠决定何时发布、发布后如何证明有用”的闭合性。**

最有价值的下一轮不是把所有未勾选项做完，而是：清理当前状态 → 统一学习判断 → 校准来源承诺 → 稳定真实集成 → 完成恢复演练 → 让目标用户连续使用。

产品定位不必推翻。可在现有“个人学习助手”定位下优先验证一个窄场景：**有明确课程或备考资料的人，能用自己的资料完成可靠练习，并在之后的复习中确认是否真正记住。** 这是建议验证的产品假设，不是已经获得用户数据支持的市场结论。
